## 本番の既存コードで確認した欠落経路
Supabase Edge Function `nar-schedule-probe` の `diagnoseHorseCells()` は公式出馬表のHTML表を取得・解析するが、現在の戻り値は `current_row_cells` と、日付の入った行を除いた `current_attribute_cells` が中心。前走の通過順列は研究に渡っていない。
`lab-claimed-context` 内 `parseNarHorseHistory()` も馬プロフィールから着順や上がりを拾うが、`early_pos` / `final_turn_pos` は取り出していない。このためLOCAL 1.6で脚質が `['?']` となる例が多い。

## 研究用実装（本番とは完全分離）
- `nar-deba-dom-columns.mjs`：出馬表の同じ馬に所属する行・同一列だけを切り出す。不明な表構造は空を返す
- `nar-deba-past-corners.mjs`：競走当日の公式出馬表と公式馬IDに紐付けて、日付がレース前の前走成績だけを解析
- `nar-deba-style-shadow.mjs`：確証を得た過去通過順を研究用脚質として算出。**FROZEN順位・能力点・EYEは変更しない**
- `nar-deba-end-to-end-shadow.test.mjs`：表の所属行→過去データ→シャドー脚質まで一貫した検証
- これらの **29ケースを保存済みコードから再実行しすべてPASS**。掲載済み公式資料の内容を写した模擬DOM／研究フィクスチャによるテストであり、生の公式HTMLに対する実行証明ではない
- 既存の過去RaceMarkTable抽出コード・上限2回の研究用読取コードは別ルートとして保管

## 欠かせない安全策
- 公式の馬リンク・当日馬番・DOM所有行・出馬表URLが一致しない場合は脚質データを使用しない
- 当日の結果や未来の走歴は入れない。人気・オッズを脚質評価に混ぜない
- 本番で確認済みの過去通過順と矛盾したら、研究値は棄却
- 過去の公式資料に載っている内容を使ったことと、事前にFROZEN生成時の利用可能データだったことは別に照合する
- 公式馬IDとして各テストに置いた lineage code はフィクスチャ上のダミーであり、実馬の識別子を検証したことを意味しない
- 生の公式HTMLへの直接GETは今回の作業環境でDNS／取得エラーとなった。**実HTTP＋DOMの整合検査と production-like source への組込試験は未実施**
- 出馬表のDOM構造が違う日・場では自動推測してずらさず、必ず `?` を残す

## なぜ能力順位をまだ変更しないのか
全LOCAL 1.6保存予想312Rで、過去アーカイブの馬名照合に基づく「先行型なら5位を入れ替える」仮ルールの結果：

### プロダクション入力境界の新しい発見
本番 `lab-claimed-context` の `safeHistory` は **過去レース日付・競馬場・レース番号・馬識別・許可された出所** を要求する。公式DebaTableの過去欄はレース番号が必ずしも分からないため、**これを無理に `recent_runs` や `history` として偽装してはいけない**。

実装した `automation/nar-claimed-context-corner-sidecar.mjs` は、公式出馬表の同じ馬行＋公式馬IDの証拠を検証したうえで、
- `shadow_card_corner_evidence`（各過去走の日付・通過順・出所）
- `shadow_running_style_reference`（逃/先/差/追/?）
- `shadow_card_evidence_status`
の **3つを研究用の別枠に保持**する。既存FROZEN・順位・評価点・正式な過去履歴は不変。

これは**研究用入力アダプターのユニットテストに合格した段階**で、まだ本番コードへの接続・モデル再評価・精度の検証は行っていない。
